# Designing proofs that can change a casting decision

## Role extraction and routes

The host authors the interpretation from source passages, not from a name alone.
RoleArchetypeProfile is an artifact, not another Character database. Its sources
pin story, candidate interpretation, current visual/stylization policies and user
direction, distinguishing their authority. Stable CharacterVisualSpec stays with
character-art; screenplay owns meaning/dialogue; DPD extracts playable tasks.

Choose order by the least established, most consequential casting claim. A face-first
lead may need FACE→SCALE→PERFORMANCE. A silhouette-dependent creature or unusually
small role can use SCALE→FACE→PERFORMANCE; scale then establishes a provisional
body identity which the face stage must retain. For an existing identity whose
visible reaction is the unresolved issue, PERFORMANCE→FACE can be appropriate,
with the existing approved reference pinned. A small conversational role may omit
scale when stature does not distinguish it; record why. Do not make all roles run
all stages. Finalists must satisfy every scheduled proof with consistent identity
lineage, regardless of order. Omitted dimensions remain outside approval scope.
Add SOCIAL between body and performance when status or belonging must be read through
others. Social proof has no universal central ruler or deferential crowd default.

## Controlled searches

FaceArchetype distinguishes geometry (for example plane width, eye/mouth relationships,
asymmetry) from intended presence. Diversity is measured by observed structures,
not number of seeds. Use the same crop, camera height, light, background, hair and
simple costume. If every result becomes one generic handsome face, call the search
insufficient; do not promote two near-duplicates to satisfy a count.

BodyArchetype uses only meaningful observable dimensions: frame size, vertical
proportion, head/body ratio, shoulder span, torso depth, waist, limbs, hands, posture,
mobility implication. Nothing defaults to large/muscular. RelativeScaleProof states
an anchor, shared ground/depth, camera control, expected relation, invalidating
cheats and uncertainty. Human peers, ordinary furniture, doorways, mounts or known
props may be appropriate. Avoid raised platforms, depth offsets, wide-angle stretching,
headgear height and costume bulk. Compare anatomy, not topknots. Generated anchors
are a fictional relative staging test, never historical centimetre measurements.
A horse or prop is not automatically standard-sized: declare/check its assumed scale.

PerformanceStateProof specifies trigger, playable task, traits retained, visible
change and misreadings. “Listen to a valid offer while trying not to yield” gives a
performer a task; “sad eyes” assigns a label. A comic, child, elderly intellectual
or maternal role can need entirely different states. Preserve selected face/body,
camera/light/costume and crop. Use prior verified Media as identity input. If framing
changes, separate that loss of comparability from performance judgment. A still
can show a state; listening, timing, speech and action remain untested.

## Handoff and selection

`CastingReview` carries current profile/conditions fingerprints, verified Media refs,
identity input refs and separate named findings. Stage criteria are conjunctive;
more beauty cannot compensate for a failed required scale or presence finding.
PERFORMANCE adds every `state:<key>` and `identity_preserved` to required findings.
FACE permits PASS/SHORTLIST; later proofs require PASS. `stage_brief` checks count,
all prior scheduled proofs and budget reservation; `user_selection_gate` intersects
qualified identities and checks cross-proof Media lineage, but cannot emit approval.
The excavation gate is also required for new generation and final user selection.
Existing archived profiles lacking excavation remain valid for read-only diagnosis.

Schema/CLI validation authenticates neither Media bytes nor user approval. Host must
resolve the cited Media, check hashes and actual generated references, review images,
and retain source review versions. Never fabricate user approval in a JSON field.
The existing freeze gate owns whether user-approved visual duties permit production.

Use local artifacts for searches and dry runs; existing Media for retained images.
No new tables, services, tool authority or casting-specific business entities.
