# People and relationships in model-facing prose

Use this method for provider-facing image/video instructions and their supplied
shot reading. Personal proper names must not occur in non-spoken executable
prose, including identity glosses, relational context, reference captions/preambles,
acting or sound directions and negatives. A different transliteration, surname,
nickname or “Y (original name)” is still a name. Keep source/author names, IDs and
provenance in Host records. This is a selected writing constraint, not a claim
about a Provider's undisclosed sensitive-word policy or a moderation guarantee.

## Resolve identity before replacing a name

In the existing preparation notes map the canonical subject/version to one
source-supported descriptive alias and its actual reference ordinal/duty. Prefer
an established role plus a distinguishing stable feature when necessary. For this
story, “雅科夫 → 年长琴手 Y” is an example, not a global character template.
Do not invent age, ethnicity, kinship, marks or costume to distinguish people.
Maintain aliases across adjacent shots; transient emotion or screen position does
not rename someone. If the same role is shared, use evidenced distinctions and
separate aliases instead of merging people.

Resolve every provider subject token against this request's source before using
it: `<主体1>` need not denote the same person in another shot. A descriptive alias
keeps the existing canonical identity, source pins, image order and same-person
trajectory. It does not replace the selected image or make one body into two.

## Replace named relations, keep their meaning

Re-express both endpoints and the relation in concrete source-grounded terms.
For example, a source sentence about an older musician leaving after his pay is
settled may become “年长琴手 Y 的当日工钱已结清，但领奏 S 未承诺再雇他；
青年长笛手 R 仍需留下接奏”, where those roles/ages are already established.
Preserve the current predicament, dependence, power, refusal or received cue that
makes the shot meaningful. Do not replace the reading with vague mood, erase
relationships, add a resolution, or turn prior circumstances into current action.
Keep the existing limit of at most two concise context paragraphs and merge
redundant alias introductions. A later single-letter alias may suffice once it is
unambiguous. Reference tokens remain tied to the same actual images and duties.

## Protect story text and historical records

Do not silently replace a name inside approved exact dialogue, song or required
on-screen text. Record that literal separately as protected story text and keep
its speaker/order unchanged. If a request also requires removing a proper name
from that locked story text, treat it as a source-text decision for the existing
Dialogue/Script owner under the user's explicit scope; alias cleanup is not that
authority. Do not add a routine approval gate for ordinary prose replacement.
Historical submitted prompts remain verbatim, with a new version for any later
candidate. A historical export must not masquerade as an alias-clean request.

## Existing Host review, after final writing and compilation

Read the full actual provider-facing text, including the context paragraphs and
compiler-added reference/sound prose. Check Chinese, transliterated and other
language name variants from the current subject inventory; a scan locates possible
residue but cannot adjudicate dialogue boundaries or semantic equivalence.
Compare each original relation with the rewritten one: actor/recipient, speaker/
listener, gaze target, prop holder, trigger/time and reference duty remain the same.
Check one-to-one identity through movement/occlusion and that no synonym introduced
a second person or shifted a task to another actor. Retain the exact source-to-
alias mapping and reviewed text hash in existing notes/source-to-module mappings.
If names or lost relations return during compilation, repair the responsible
professional source or final-writing module and recompile through the same path.
Never patch a sealed request, add an alternate prompt or claim offline success
proves what a generation model will do. This is part of the current Host review,
not a new workflow, runtime field, blocker or permission to generate.
